This document translates requirements into concrete design decisions for the first two core systems. It is intended to be read alongside the Requirements Document and updated as implementation reveals design problems.
1. Document Overview
This design document covers two foundational systems that must be implemented before any other game system can function: the Building System and the Power Network. Every other system in Space Crusade depends on these two working correctly. Getting them right — and getting them right early — determines the quality of everything built on top of them.
Each section follows the same structure: a summary of what was decided in the requirements doc, the concrete design decisions that translate those requirements into implementable behaviour, the data schemas needed to support the system, and any open questions that must be resolved before coding begins.

2. Resolved Design Decisions
The following questions were flagged as open in the requirements document. They are answered here before detailed design begins, because later sections depend on them.
✅  Decision — Camera perspective:  Top-down with free zoom. The camera sits directly above the world and can zoom from a close block-level view to a wide base-overview distance. The player character is visible as a small figure. This matches the factory genre, makes build layout readable, and avoids the complexity of a 3D orbit camera in V1. Third-person perspective can be reconsidered for a future version.
✅  Decision — Structural integrity model:  Connectivity-only (Option A). Blocks are valid as long as they connect to the construct via at least one adjacent face. No weight or stress simulation. Floating cantilevered structures are permitted. This is the correct choice for V1 — it is fast to validate, easy to reason about, and keeps the focus on factory design rather than structural engineering.
✅  Decision — Power shortage behaviour:  Proportional throttle with one exception: turrets are protected. When supply falls below demand, all non-turret consumers are slowed proportionally. Turrets always receive full power as long as any supply exists. This gives the player a useful signal (machines slow down) while preserving defensive capability during shortages, which feels fair and strategically interesting.
✅  Decision — Multi-grid alignment:  Separate foundation grids are always independent and cannot be merged. Each foundation group defines its own coordinate space. This eliminates a complex edge case entirely. The practical implication is that the player must plan their base layout on one continuous grid from the start, or accept that two separate grids are two separate constructs.
3. Building System
3.1 Grid
The world grid is a uniform 3D lattice with a fixed cell size. One cell is the smallest unit of space in the building system. Everything — block size, connection ranges, conveyor lengths — is expressed as multiples of this unit.
✅  Decision — Cell size:  1 metre × 1 metre × 1 metre. This is a logical unit only; visual scale may differ.
✅  Decision — Grid origin:  Each foundation group establishes its own local grid origin when the first foundation block is placed. The local origin sits at the centre of that block&apos;s bottom face. All subsequent blocks in the group snap to integer offsets from this origin.
✅  Decision — Y-axis:  Y increases upward. Blocks can be placed at any integer Y position above terrain, enabling multi-storey structures.
3.2 Block Placement
Placement is a three-phase operation: preview, validate, confirm.
During preview, the selected block type is shown as a ghost at the player&apos;s cursor position. The ghost snaps to the nearest valid grid position. Rotation is applied before snapping. The ghost colour indicates validity: green for valid, red for invalid.
Validation runs every frame while the ghost is active and again at the moment of confirm. The validation checks are run in this order:
All required grid cells are unoccupied.
The placement position is within a buildable area (terrain support or adjacent construct).
At least one face of the new block is adjacent to an existing block in the same construct, OR the block is a foundation being placed on terrain. The first foundation in a new group is exempt from the adjacency rule.
No block-specific placement constraints are violated (e.g. a miner must be over a resource node).
If validation fails, the ghost stays red and a one-line reason is shown in the HUD. Confirm is ignored while the ghost is red. The player does not need to re-select the block; they simply move the cursor until the ghost turns green.
❓  Open — Block rotation increments:  Should blocks rotate in 90° steps only, or also support 45°? 90° is simpler to validate and aligns with grid adjacency. 45° enables diagonal layouts but requires significantly more complex adjacency and connection logic. Recommendation: 90° only for V1.
3.3 Constructs
A construct is the runtime entity that owns a set of connected blocks. The construct is the unit of simulation: power networks, logistics networks, and vehicle physics are all properties of a construct, not of individual blocks.
Membership
Two blocks are in the same construct if and only if a path of face-adjacent blocks exists between them. Membership is recalculated whenever a block is added or removed. On removal, the system runs a flood-fill from every block that was adjacent to the removed block. If the flood-fills produce disconnected groups, each group becomes a new construct. This is the split operation.
On placement, if the new block is adjacent to two or more existing constructs, those constructs merge into one. The merged construct inherits the networks and state of both parents with conflicts resolved as described in the Power Network section.
📝  Design Note:  Split and merge operations need to be efficient. For V1, a full flood-fill on every block change is acceptable if the maximum construct size is kept small. For larger bases, an incremental connectivity structure (e.g. union-find) will be necessary. Flag this for the technical design phase.
Classification
Constructs are auto-classified each time their block composition changes:
Vehicle — contains a Control Seat block AND at least one Propulsion block AND is not terrain-anchored.
Base — terrain-anchored (contains at least one Foundation block) AND contains at least one of: production machine, storage, power generator.
Outpost — terrain-anchored, no production machines or generators, primarily logistics/extraction.
Structure — anything that doesn&apos;t fit the above. Walls, defences, unfinished builds.

3.5 Blueprint System
A blueprint is a snapshot of a region of blocks: their types, positions relative to the blueprint origin, and orientations. It contains no runtime state — no inventory contents, no machine progress.
Saving a Blueprint
The player enters Build Mode, switches to Blueprint sub-mode (Shift+B), then drag-selects a bounding box. All blocks within the box are captured. The player names the blueprint and it is saved to the blueprint library.
Placing a Blueprint
The player opens the blueprint library from the Build Mode menu and selects a saved design. A ghost of the entire design appears at the cursor. The ghost shows each block individually coloured:
Green — block can be placed, materials available in inventory or connected storage.
Yellow — block can be placed, but required materials are missing.
Red — block cannot be placed due to terrain conflict or occupied cell.
The player can place the blueprint partially. Blocks are placed in layer order (bottom to top) when the player confirms. Missing-material blocks are skipped and left as ghost markers. The player can return later to complete them once materials are available.
📝  Design Note:  The partial placement behaviour is important for large blueprints that the player does not yet have resources to complete. It avoids the frustrating experience of the whole blueprint being rejected because one expensive block is missing.

5. Power Network
5.1 Power Unit
All power values use kilowatts (kW) as the unit. The simulation runs at a fixed tick rate and energy is tracked as power (rate) rather than stored energy, except for batteries which track stored kilojoules (kJ). One second of 1 kW consumption = 1 kJ drained from a battery.
✅  Decision — Simulation tick rate:  20 ticks per second (50ms per tick). Power balance is recalculated every tick. Machines execute their production logic every tick. This gives sufficient resolution for smooth power animations without being computationally expensive.
5.2 Network Graph
Each power network is a graph where:
Nodes are power-interface blocks (poles, generators, consumers with direct connections, batteries).
Edges are wire connections between nodes within range.
Two power networks are distinct if no edge path connects them. When a new wire connection is formed between two previously unconnected nodes from different networks, those networks merge immediately. When a wire is removed, the affected network is re-evaluated for connectivity via flood-fill. If the result is two disconnected components, they become separate networks.
5.3 Wire Connection Rules
A wire connection forms automatically between two pole or power-interface blocks when:
Both blocks have power_interface ≠ none.
The distance between block centres is ≤ the smaller of the two blocks&apos; wire_range values.
The connection count of neither block would exceed its max_connections limit.
Wire connections are bidirectional. Players do not manually draw wires — connections form and break automatically as poles are placed and removed. Players manage range and connectivity by choosing pole placement, not by routing individual wires.
📝  Design Note:  Auto-wiring is a deliberate simplification. Manual wiring (like Factorio&apos;s copper cables) is more expressive but adds significant UX complexity. Auto-wiring within range keeps the focus on pole placement strategy rather than wire management. Revisit if players feel a lack of control over network topology.
5.4 Power Balance per Tick
Every tick, for each power network:
Sum the output of all connected generators currently operating → total_supply.
Sum the draw of all connected consumers that want to operate → total_demand.
Compute surplus = total_supply − total_demand.
Then apply the following rules in order:
Condition
Behaviour
surplus ≥ 0
All consumers operate at full rate. Excess power charges connected batteries up to their capacity.
surplus &lt; 0, batteries available
Batteries discharge to cover the deficit (up to their max discharge rate). If batteries cover the full deficit, all consumers still operate at full rate.
surplus &lt; 0, batteries empty or absent
Turrets operate at full rate (protected). All other consumers are throttled proportionally: operating_rate = total_supply / total_demand_excluding_turrets. Machines run at this fraction of their normal speed.
total_supply = 0
Turrets offline. All consumers offline. Network is dead.
5.5 Battery Behaviour
Batteries act as buffers in the network. They have two states per tick:
Charging — when network has surplus, batteries absorb up to their max_charge_rate (kW) until full.
Discharging — when network is in deficit, batteries supply up to their max_discharge_rate (kW).
Battery charge is stored in kJ. Each tick: stored_kJ += (charge_rate − discharge_rate) × tick_duration. stored_kJ is clamped to [0, capacity_kJ].

5.6 Power UI
The power HUD element is always visible when the player is near a powered construct. It shows:
Network name (auto-generated from construct name + &quot;Power Grid #N&quot;).
Current supply bar (green fill to total_supply).
Current demand bar (orange fill to total_demand).
Surplus/deficit value in kW.
Battery charge percentage if any battery is on the network.
When a machine is throttled due to shortage, a small orange lightning bolt icon appears on the machine&apos;s block in the world. Hovering the block shows its current operating rate as a percentage.
When the player places a power pole in Build Mode, the wire connection visualisation is always active — they can see which poles are in range and how the network would change if they placed here.

6.2 Key Technical Risks
The following aspects are the most likely sources of unexpected complexity during implementation. They are flagged here so they can be prototyped early.
Construct split/merge performance — flood-fill on large constructs is O(n). Test with the largest base size expected in V1 early. If it causes frame drops, switch to union-find.
Power network merge on construct join — when two constructs merge, their power networks may or may not be connected depending on where the joining block is. The merge logic must re-evaluate network connectivity, not assume all networks from both constructs become one.
Ghost preview performance — rendering a full ghost for a large blueprint every frame could be expensive. Consider rendering ghost blocks as instanced meshes with a shared material pass.
Grid snapping on uneven terrain — foundation blocks must snap to terrain surface, not to a fixed world-space Y. The snapping logic needs to raycast against terrain and find the nearest valid flat cell. Test on varied terrain early.
